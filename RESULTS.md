# Final Evaluation Results

This file records the headline numbers from the **full 497-resume run** of
the multi-agent pipeline on the Kaggle resume corpus
(`data/processed_main/test.jsonl`), executed with
`llama-3.2-3b-instruct` running locally via LM Studio
(`http://localhost:1234/v1`) and the dense
`sentence-transformers/all-MiniLM-L6-v2` skill encoder.

All numbers below come from artefacts under
`artifacts/main_multi_agent_lmstudio/`. The run is deterministic given
the same prompts + model + ontology because every LLM completion is
keyed in `data/llm_cache.sqlite`.

## 1. Classification (E1)

| Path | Accuracy | Precision (macro) | Recall (macro) | F1 (macro) | F1 (weighted) | Support |
|---|---:|---:|---:|---:|---:|---:|
| Baseline TF-IDF + Logistic Regression | 0.6398 | 0.6536 | 0.6064 | 0.6115 | 0.6373 | 497 |
| **Agents-only** (deterministic scorer over LLM-extracted features) | **0.2153** | 0.2564 | 0.1953 | 0.1884 | 0.2083 | 497 |
| **Ensemble** (agents + LinearSVC + baseline vote) | **0.6821** | 0.6794 | 0.6422 | **0.6361** | 0.6669 | 497 |

Deltas:

- Ensemble - Baseline: **accuracy +4.23 pts**, F1_macro +2.46, F1_weighted +2.96.
- Agents-only - Baseline: **accuracy -42.45 pts** — the deterministic agent path under-performs on its own.
- Ensemble - Agents-only: accuracy +46.68 pts.

**Decision-source breakdown** (whose vote produced each ensemble row):

| source | count | share |
|---|---:|---:|
| `supervised+baseline-agree` (LinearSVC == TF-IDF baseline) | 383 | 77.1% |
| `supervised-agent` (LinearSVC != baseline; SVC wins) | 114 | 22.9% |
| `multi-agent` (agent stack overrode the baseline) | 0 | 0.0% |
| `ensemble-agree` (agent == baseline) | 0 | 0.0% |
| `baseline-prior` | 0 | 0.0% |

The +4.23 pt gain over the baseline is driven entirely by the LinearSVC,
not by the LLM agents. The agent stack contributes no winning votes
under the current job-profile + ontology coverage.

## 2. Skill extraction (E2)

Computed on the 96-resume gold subset
(`data/annotations/skills_gold.jsonl`, 1490 gold canonical skills).

| Aggregate | Precision | Recall | F1 | Support |
|---|---:|---:|---:|---:|
| canonical macro (per-resume avg) | 0.703 | 0.218 | 0.287 | 96 resumes |
| canonical micro (over all skill instances) | 0.580 | 0.226 | 0.325 | 1490 skill instances |

Reading: the multi-agent pipeline is **high-precision, low-recall** on
canonical skills — when it labels a skill it's right ~58–70% of the
time, but it only catches ~22% of what the gold annotations contain.
This is consistent with the conservative `min_confidence=0.4` threshold
and the tightened "what counts as a skill" prompt.

## 3. Ranking (E3) — per-category fit-score retrieval

For each of the 24 occupational categories C, all 497 test resumes were
ranked by `fit_score(resume, profile=C)` and scored against the binary
relevance `1[true_label == C]`. Macro-averaged across the 24 jobs:

| k | Precision@k | Recall@k | MAP@k | nDCG@k |
|---:|---:|---:|---:|---:|
| 1 | 0.2917 | 0.0131 | 0.2917 | 0.2917 |
| 3 | 0.1528 | 0.0204 | 0.1435 | 0.1811 |
| 5 | 0.1500 | 0.0338 | 0.1124 | 0.1716 |
| 10 | 0.1375 | 0.0660 | (truncated) | (truncated) |

The system retrieves the right top-1 candidate ~29% of the time, but
recall climbs slowly with k — again the consequence of generic job
profiles failing to discriminate non-tech categories.

## 4. Fairness audit (perturbation-based)

Generated by feeding name / pronoun / identity-cue perturbed copies of
each resume through the full agent pipeline and comparing the
deterministic `fit_score` against the ensemble-chosen job:

| Statistic | Value |
|---|---:|
| n_pairs | 497 |
| original mean fit_score | 28.16 |
| perturbed mean fit_score | 29.38 |
| **mean score difference** | **+1.22** |
| score-difference 95% bootstrap CI | [0.26, 2.29] |
| selection rate (threshold = 60) original vs perturbed | identical |
| **selection-rate difference** | **+0.002** |

The selection-rate delta is essentially zero. The score delta is small
(~1 point on a 100-point scale) but its 95% bootstrap CI excludes 0, so
it is statistically detectable. This is consistent with the system
being **largely identity-blind by construction** in the deterministic
scorer; the residual delta probes the LLM rationale and any
identity-leaking text-similarity component.

## 5. Rationale quality (NEW evaluation)

Every LLM-authored rationale and recommendation across the 497 records
was audited on grounding, specificity, calibration and identity terms.
Metric definitions in
`@/Users/sriram/Desktop/Development/spring2026/Data mining/finalproject/dm_project/src/eval/rationale_quality.py`.

| Metric | Old prompt (100-resume run) | **New prompt (full 497 run)** | Change |
|---|---:|---:|---|
| `n` | 100 | **497** | — |
| `grounded_in_matched_pct` (rationale cites ≥1 candidate skill) | 56% | **66%** | +10 pts |
| `grounded_in_missing_pct` (rationale cites ≥1 gap) | 77% | **100%** | +23 pts |
| `grounded_in_both_pct` | 55% | **66%** | +11 pts |
| `specific_pct` (≥15 words) | 100% | **100%** | — |
| **`calibrated_pct`** (recommendation tone matches fit-band) | **7%** | **41%** | **+34 pts (5.9x)** |
| `identity_clean_pct` (no demographic terms) | 100% | **100%** | — |
| `avg_word_count` | 32.7 | **41.9** | +9 words |
| `strengths_grounded_pct` (% of `strengths` arr. that map to `matched_skills`) | 86% | 55% | -31 pts |
| `gaps_grounded_pct` (% of `gaps` arr. that map to `missing_skills`) | 98% | **99.6%** | +1.6 pts |

Tone vs band distribution (full run):

| | advance | consider | reject | unclassified |
|---|---:|---:|---:|---:|
| LLM-produced recommendation tone | 58 | 285 | 100 | 54 |
| `fit_score` band (truth) | 0 | 130 | 367 | — |

The remaining calibration gap is mostly in the **reject band**: 367
candidates have `fit_score < 40` (deterministic reject), but the LLM
still produced "consider"-tone recommendations for the bulk of them.
The new prompt's explicit band -> tone mapping fixed the worst
miscalibration (advance-tone for low-score candidates dropped from 54%
to 12%) but the LLM still leans nice on borderline rejects.

The drop in `strengths_grounded_pct` (86% -> 55%) is a side-effect of
the new prompt asking for richer strengths arrays drawn from both
`matched_skills` and experience signals (years, leadership). Strings
like "11 years experience" don't string-match a canonical-skill name,
so they count as "ungrounded" by this rule-based check even though
they're legitimately drawn from the candidate's signals. The
`gaps_grounded_pct` is unaffected (99.6%) because gaps still come only
from `missing_skills`.

## 6. Identity-blindness

`identity_clean_pct = 100%` over 497 records — no rationale used a
gendered pronoun, marital status, age descriptor, religion, ethnicity
or disability-related term. This is a non-trivial property given the
LLM was given resumes that often contain such cues; the tightened
evaluator prompt's explicit demographic exclusion list held.

## 8. Honest takeaways for the writeup

1. **The +4.23 pt ensemble lift over the baseline is real and reproducible**, but the `decision_source_breakdown` shows it is **entirely produced by the LinearSVC**, not the LLM agents. The agents-only path is at 0.215 accuracy — well below the baseline's 0.640.
2. **The agents-only weakness is structural, not implementation-bug.**
   Three independent root-cause fixes were applied this session (ChromaDB
   L2->cosine, skill-miner threshold 0.2->0.4, evaluator prompt
   tightening, two job-profile rewrites), driving smoke-set agents-only
   accuracy from 5% -> 24%. The remaining failure mode is the
   141-entry ontology and the 24 hand-curated job profiles, both of
   which lack domain coverage for ADVOCATE, AGRICULTURE, APPAREL,
   AUTOMOBILE, BANKING, CHEF, FINANCE, HEALTHCARE, PUBLIC-RELATIONS,
   TEACHER (all at 0% agents-only on the 100-resume sample).
3. **The multi-agent system's contribution is explainability, not classification accuracy.**
   The rationale-quality numbers below back this up:
   - Every rationale cites a real gap (100% grounded in missing skills).
   - 66% explicitly cite a candidate skill they have.
   - 100% are identity-clean (no demographic terms).
   - 41% are calibrated to the deterministic fit score band.
   These properties are not achievable by the TF-IDF baseline at all.
4. **The pipeline is deterministic and reproducible.** Re-running the
   full 497-resume evaluation hits the LLM cache and finishes in
   seconds; deleting `data/llm_cache.sqlite` triggers a full ~100-minute
   re-run. The same artefacts are produced on every re-run.
5. **Skill-extraction precision (0.70 macro) is good; recall (0.22) is intentionally low.**
   The current min_confidence=0.4 threshold trades recall for precision.
   The gold annotation file is auto-labelled and not yet
   human-reviewed (`review_status="auto"`); per-resume P/R/F1 should be
   treated as machine-against-machine until at least a 50-resume
   reviewer pass is done.

## 11. Iteration v3 — Learned profiles + V4 ensemble + soft-match exploration

After the headline run above, three improvements were trialled and a
fresh full 497-resume evaluation was produced under
`artifacts/main_v3_soft_match/`. The three changes are:

1. **Data-driven (learned) job profiles** built by alias-substring
   scanning over the 2 003-resume training corpus
   (`@/Users/sriram/Desktop/Development/spring2026/Data mining/finalproject/dm_project/src/models/profile_builder.py`).
   The 24 hand-curated profiles in `src/data/jobs.py` are replaced at
   evaluation time with profiles whose `must_have` / `nice_to_have`
   skill lists are the most-frequent canonical-ontology hits in the
   training resumes for that job. Loaded by passing
   `--learned_profiles data/profiles_learned.json` to the runner.
2. **V4 ensemble override rule** in `_ensemble_choice`
   (`@/Users/sriram/Desktop/Development/spring2026/Data mining/finalproject/dm_project/src/eval/evaluation_runner.py:438-466`).
   When the LinearSVC and the agent path agree but disagree with the
   TF-IDF baseline, the agent+SVC vote now wins under a low-margin
   condition. This is the first time the agent path contributes to
   the ensemble decision in production.
3. **Soft semantic skill matching** in
   `@/Users/sriram/Desktop/Development/spring2026/Data mining/finalproject/dm_project/src/models/scoring.py`
   (`soft_skill_overlap`): a candidate skill counts toward profile
   coverage when its MiniLM-L6 cosine similarity to any profile skill
   exceeds `SOFT_MATCH_THRESHOLD`. The threshold was swept by
   `@/Users/sriram/Desktop/Development/spring2026/Data mining/finalproject/dm_project/scripts/threshold_sweep.py`.

### 11.3 Soft-match threshold ablation (negative result)

`scripts/threshold_sweep.py` sweeps `SOFT_MATCH_THRESHOLD`, holding all
other components fixed (cached agent outputs + refit LinearSVC).

| threshold | agents-only | ensemble | overrides | note |
|---:|---:|---:|---:|---|
| 2.00 (exact only) | **0.2938** | 0.6841 | 16 | best agents-only |
| 0.70 | 0.2938 | 0.6841 | 16 | no soft match fires |
| 0.60 | 0.2877 | 0.6821 | 17 | |
| 0.55 | 0.2817 | 0.6821 | 15 | |
| 0.50 | 0.2596 | **0.6861** | 17 | best ensemble (single-resume noise) |
| 0.45 | 0.2354 | 0.6841 | 16 | as run in `main_v3_soft_match/` |
| 0.40 | 0.2394 | 0.6841 | 16 | |

Soft matching **monotonically hurts** agents-only accuracy
(0.294 → 0.235 going from exact to threshold 0.45) because the cosine
fallback dilutes the per-profile argmax discrimination. The single
threshold that beats exact on ensemble (0.50, +0.20 pts) does so by
flipping a single override and is within run-to-run noise.

**Decision**: ship soft matching as code (the implementation, the unit
test in `@/Users/sriram/Desktop/Development/spring2026/Data mining/finalproject/dm_project/scripts/test_soft_overlap.py`,
the inspection in `scripts/inspect_cosine_pairs.py`, and the threshold
sweep) but set the production default to `SOFT_MATCH_THRESHOLD = 1.01`
in `@/Users/sriram/Desktop/Development/spring2026/Data mining/finalproject/dm_project/src/models/scoring.py`.
This effectively reverts to exact set intersection, which the ablation
showed is Pareto-optimal on this corpus. Future ontology expansions
that add more near-synonym pairs may justify lowering it.

### 11.5 Per-k retrieval ranking regression

| k | Old P@k | v3 P@k | nDCG@k old | nDCG@k v3 |
|---:|---:|---:|---:|---:|
| 1 | 0.2917 | 0.1250 | 0.2917 | 0.1250 |
| 3 | 0.1528 | 0.1806 | 0.1811 | 0.1667 |
| 5 | 0.1500 | 0.1417 | 0.1716 | 0.1436 |
| 10 | 0.1375 | 0.1333 | — | 0.1373 |

The top-1 retrieval drop is the one place learned profiles **hurt**.
The data-driven profiles share more canonical skills across jobs
(e.g. `python` appears in many learned profiles), so the per-job
`fit_score` ranking is less discriminative at k=1. P@3 actually
improves; the regression is concentrated in the strict top-1 case.
This is a known cost of moving from hand-curated to data-driven
profiles, documented for future work (e.g. profile-pruning or IDF-style
skill weighting).
